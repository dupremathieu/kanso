# Decisions

Small choices the plan leaves open, recorded as one line each.

- CLI usage errors exit 1 (clap defaults to 2) to match PLAN §6; API/conflict exit codes 2/3 arrive with the CLI in M4.
- `/api/health` returns HTTP 503 with `{"status":"error","version":"…","db":"error"}` when `PRAGMA quick_check` fails; the plan only defines the healthy shape.
- The health `quick_check` result is cached for 5 s and refreshed single-flight, so unauthenticated probes cannot saturate the blocking pool.
- Static assets are read from `web/` next to the executable, falling back to `./web`; startup fails fast when `index.html` is absent.
- `/api` paths never fall back to `index.html`; missing paths with a file extension return 404, extensionless paths serve the shell.
- All static responses use `Cache-Control: no-cache` until asset URLs are fingerprinted.
- `PRAGMA synchronous=NORMAL` is set alongside WAL, following the corruption mitigation in PLAN §13.
- `serve --port` replaces the port in `KANSO_BIND` and `--data-dir` overrides `KANSO_DATA_DIR`; there is still no config file.
- The crate is split into `src/lib.rs` plus a thin `src/main.rs` so the M1 in-process API tests can import the router.
- The runtime image uses `alpine:3.24` instead of PLAN §10's `3.21` because 3.21 reached end of support on 2026-11-01; the builder is pinned to `rust:1.99-alpine`.
- The container healthcheck derives its port from `KANSO_BIND` and allows 10 s, while the default check interval remains 30 s.
- No `anyhow` or `tempfile` dependency: a small `Error` type and std temporary directories cover the scaffold.
- Session cookies are `session_id.hmac_sha256_base64url`; the HMAC key is a random 32-byte `session.key` in the data directory, created atomically with mode 0600 and independent of `KANSO_PASSWORD`, so sessions survive restarts and deleting the file revokes them all.
- UI sessions expire 30 days after login; `last_seen` slides at most once per hour, but does not extend `expires_at` (the milestone says `expires_at` 30 days and `last_seen` sliding).
- The login limiter allows five attempts per client per 60 s and resets on success. With the loopback nginx proxy, the key is `X-Real-IP` (then the last `X-Forwarded-For` hop); direct non-loopback connections use the socket address and ignore forwarded headers.
- `GET /api/projects?archived=1` returns active and archived projects; the default excludes archived ones.
- Task list ordering uses the board order (`backlog, todo, in_progress, in_review, blocker, done`) rather than SQLite's lexical status order, then rank and number.
- `PATCH` payloads use `deny_unknown_fields`, so `status`, `rank`, `project_id` and other non-editable fields are rejected with `validation` (400) rather than silently ignored; `due_date: null` clears the date.
- Checklist `before`/`after` name neighbouring item ids: `after` is the item that precedes the moved item and `before` the item that follows it. When both are present they must be in that order; a gap below `2 * MIN_GAP` renumbers the checklist inside the transaction.
- Comments and activity rows use `ui` for the password session and the token name for bearer tokens; task `created_by` follows the same rule. An agent token's `X-Kanso-Agent` header substitutes the display name for these attributions (see the M4 section); claim ownership keeps the token name.
- Token names are trimmed and limited to 64 characters (the plan sets no limit); token `last_used_at` is refreshed at most once per minute, session `last_seen` at most once per hour.
- API token hashes are stored as lowercase SHA-256 hex and are never returned; only `POST /api/tokens` returns the plaintext token, once.
- Internal failures return `500` with code `internal` and a generic message; details are logged server-side. Serde data errors (Axum's 422) are mapped to `400 validation`, while 413/415 keep their status and use the `validation` code.
- M1 follows the milestone brief for hard deletion: `DELETE /api/tasks/:ref?hard=true` requires the flag and a human identity. The extra confirmation header described in PLAN §4 is deferred to the API/UI work that can send it.
- Task numbers follow the brief's `max(number) + 1` inside the create transaction. Hard-deleting the highest-numbered card therefore allows that number to be reused; a permanent per-project counter is not part of M1.
- Agent scope in M1 is deliberately the milestone subset: read projects/tasks/labels, comment, and add or update checklist items (reordering included). Checklist deletion and all task/project/label/token writes are human-only until M2's move/claim work; `GET /api/tokens` is also human-only.
- The new dependencies are `hmac` + `sha2` for HMAC-SHA-256 session signatures (with RFC 4231 test vectors), `getrandom` for OS randomness, and `base64` for URL-safe token and cookie encoding; no cryptography is hand-written.
- `/api/events` accepts a cookie or a bearer token (the milestone brief overrides PLAN §5's cookie-only wording). Each connection revalidates its session/token once per heartbeat interval (25 s by default) and closes after 30 minutes, so logout, expiry and revocation stop an existing stream without pinning a connection forever.
- SSE event IDs are allocated and broadcast under one mutex, so subscribers see strictly increasing IDs. The sequence is process-local and restarts at 1 on restart; clients refetch on reconnect instead of relying on IDs for gap recovery.
- A subscriber that lags the 256-event broadcast ring, or whose per-connection channel fills, is disconnected; publishers never wait. Auth/session and token events are not broadcast because agent-scoped SSE subscribers must not learn token metadata.
- The SSE heartbeat is a `: heartbeat` comment every 25 s. A client that stops reading entirely also stops hyper polling the response body, so that case is bounded by the deployment's proxy/TCP timeouts rather than by a Rust timer.
- `/api/tasks` defaults to `state='active'`; archived cards require an explicit `?state=archived` and proposals an explicit `?state=proposed`. The board and `/api/agent/next` also only consider active cards.
- `POST /api/tasks` from an agent token always creates a proposal (`state='proposed'`, `status='backlog'`, `source='agent'`) and ignores the payload's `status`; the activity kind is `proposed` and the event is `proposal.created`.
- Accepting a proposal defaults to `backlog` and appends to the target column's end. Accept/reject require `state='proposed'`; anything else is `409 not_proposed`. Rejection archives the card (`archived_at` set) and records `rejected`.
- `move` treats `after` as the preceding card and `before` as the following one. When both are sent they must be adjacent among the visible active cards; archived/proposed cards may sit between them in rank order and do not make the move invalid.
- Rank computation for a move uses only active cards, so hidden cards cannot shift visible order. Restoring an archived card whose rank duplicates a visible card renumbers the active column `1..n`; `task.moved`, `task.archived` and `task.restored` include the resulting ordered `column` so SSE clients need no refetch for renumbering.
- Moving an active card to `blocker` stores the previous status in `blocked_from`. `restore:true` is valid only from `blocker` and returns to `blocked_from`; an explicit `status` wins over `restore`; a move with neither clears `blocked_from`/`blocked_reason` but leaves the card in `blocker`. Entering `done` sets `done_at` and leaving it clears it. A same-status move on a non-blocker card only reorders; a blocker card with neither `status` nor `restore` also clears its blocker metadata.
- Moving a non-active card is `409 not_active`. Agents may move only when both the current and target status are in `todo`, `in_progress`, `in_review`, `blocker`; everything else is `403 forbidden`.
- Claim failures use `409 already_claimed` (a claim exists), `not_claimable` (wrong state/status) and `dependency_unmet` (some `blocked_by` card is not `done`). Release of an unclaimed card is `409 not_claimed`; an agent releasing another identity's claim is `403 forbidden`.
- Token names are case-insensitively reserved for `ui` so an agent token cannot impersonate a browser session and pass the own-claim release check.
- `/api/agent/next` returns `204 No Content` when nothing is available and `404 not_found` for an unknown `project` filter. It excludes cards from archived projects and sorts in Rust with a unit-tested comparator (priority, due date with NULLs last, rank, number). `claim=1` from a cookie session requires the usual origin check because the method is GET.
- Dependencies are human-only in M2. The endpoint replaces the whole set, deduplicates references, allows cross-project edges, rejects self-dependencies and cycles with `400 validation`, and returns `404 not_found` for unknown references. Cycle detection is a depth-first walk (explicit stack) over the remaining graph after removing the card's outgoing edges.
- `GET /api/projects/:id_or_key/board` returns `{project, columns}`; `GET /api/board` returns `{projects:[{project, columns}]}` (the "same shape per project"). The global view lists active projects in position order; `?project=` resolves one project even if archived. Columns are always the six fixed keys, with active cards ordered by rank then number.
- Board cards expose `id`, `reference`, `title`, `status`, `priority`, `due_date`, `labels`, `claimed_by`, `attention`, `session_status`, `blocked_from`, `checklist_done`, `checklist_total` and `blocked`, not the full detail.
- Event payloads use `data.task` for task summaries, `data.project` for projects, `data.label`/`data.comment`/`data.item` for the corresponding objects, and `data.task_id` where only an id is needed. Checklist updates carry the full reordered `checklist` because a renumber rewrites siblings; dependency changes carry the full `dependencies` object.
- M2 keeps task archive/restore human-only. PLAN §5's authorization matrix allows an agent to archive a card it created or claimed, but PLAN §2 says agents may not archive; the stricter §2 rule is kept until the ownership rules are made explicit in a later milestone.
- `GET /api/inbox` is readable by agent tokens as well as humans (agents need to see their own proposals), while accept/reject stay human-only.
- M3 adds three additive board-card fields: `checklist_done`, `checklist_total` and `blocked`. The M3 card specification requires checklist progress and a blocked lock on every card, which the M2 card shape could not supply without one detail request per card; no existing field or endpoint behaviour changed. Migration v2 adds `checklist(task_id)` so the board aggregate starts from the checklist rows instead of scanning that table for every project.
- The shell uses History API routes with the server's existing `index.html` fallback. A project route reads `/api/board?project=KEY`, the global route reads `/api/board`; both share the same client store, so switching views does not need a second representation.
- `web/i18n/en.js` is the only place with English text. Its `messages` object is flat, `translate(dictionary, key, vars)` interpolates `{name}`, and `web/i18n/index.js` is the one import site for components. Adding `fr.js` means copying `en.js`, translating the values and changing the re-export in `index.js`.
- `marked` is vendored at 15.0.12 (UMD `marked.min.js`) and loaded as a classic script before the module. Raw HTML is escaped by a renderer override, then the output is parsed in a `<template>` and passed through an allow-list sanitizer: script/style/iframe/object/svg/media/form nodes are removed, only `href`/`title`/`code class`/`ol start`/table alignment attributes survive, `javascript:`/`data:` hrefs are dropped, images are replaced by their alt text (the UI may not load external resources), and links open in a new tab with `rel="noopener noreferrer"`. This sanitized Markdown insertion is the only `innerHTML` in the UI.
- All other rendered values use `textContent`/DOM APIs. Icons are inline SVG built with `createElementNS`; there are no icon fonts, CDN links or web fonts.
- `index.html` keeps `{{VERSION}}` on the stylesheet, module and vendored Markdown URLs. Relative imports between ES modules are not version-suffixed, but every static response is `no-cache`, so browsers revalidate imports on reload; a deploy between module fetches is bounded by normal cache revalidation rather than by fingerprinting.
- Board drag & drop uses pointer events only: 5 px mouse threshold, 250 ms touch long-press (a plain touch scroll is left alone), floating ghost, dashed placeholder, edge auto-scroll, Escape cancellation and `setPointerCapture`. Drops are applied optimistically and reconciled from the `move` response plus the `task.moved` ordered `column`.
- Panel width (320–640, default 420) and the collapsed flag live in `localStorage`. The panel overlays the board at ≤1100 px and columns become 85 vw at ≤700 px, as PLAN §8 specifies.
- SSE reconnects manually with exponential backoff from 1 s to 30 s. Every successful stream open after the initial load performs a core + board + open-card refetch, covering events missed between the first fetch and the open as well as reconnect gaps. A clean server-side stream end (the 30-minute lifetime) probes `/api/me` and reconnects silently; a failed probe shows the offline toast. Task/project/proposal/label events patch the local store; checklist/comment events reload an open card and debounce a board refresh so card progress counters stay correct.
- Browser notifications are opt-in through the bell control only; permission is never requested during page load, and a notification fires only while the tab is hidden when a card gains `attention` or enters `in_review`.
- `tests/ui.rs` is an integration test for the static shell: it requests `index.html` and its deep links, every URL the shell references, every ES module (including `i18n/index.js`), and `vendor/marked.min.js`, checks their content types, compares the module inventory with every `.js` file under `web/`, and asserts a missing `.js` asset never falls back to the SPA.

## M4 — CLI, agent header and skill

- The three M4 API additions are additive: `POST /api/tasks/:ref/session` (human only, default status `running`), an optional `reason` on `POST /api/tasks/:ref/move`, and `POST /api/backup` (human only). No existing route, field or event changed.
- `reason` is trimmed and limited to 500 characters. It is valid only for a target of `blocker`; sending it with any other target is `400 validation`. Entering `blocker` without a reason clears stale text, an already-blocked card can update its reason, and leaving `blocker` (or the in-place blocker clear) always clears `blocked_from`/`blocked_reason`.
- Session link validates a non-empty session id (200 characters) and directory (4096 bytes). It stores `session_id`, `session_directory`, `session_status`, records the `session_linked` activity and broadcasts `task.updated`; there is no separate event type.
- `X-Kanso-Agent` is honoured only for agent-scope bearer tokens. A human token or UI session ignores it. For an agent token it must be non-empty, at most 64 characters, free of control characters and not case-insensitively `ui`; otherwise the request is `400 validation` (never silently ignored). The header changes only the display attribution (`comments.author`, `activity.actor`, `created_by`); `claimed_by` and release ownership keep using the token principal so one agent cannot take over another token's claim by spoofing a name.
- `POST /api/backup` accepts an empty body, `{}` or `{"dir": "…"}`. `dir` may be relative (resolved under the data directory) or absolute (accepted only inside it); `.` and `..` are normalised lexically and an existing target directory is canonicalised so a symlink cannot escape. Files are named `kanso-YYYYMMDD-HHMMSS-<uuid>.db`; the random suffix makes names unique across processes, and a failed `VACUUM` removes only that attempt's partial file. The copy is fsynced and the response is `{path,size,created_at}` with the server-side path. `VACUUM` runs through the single serialized SQLite connection, so one large backup briefly blocks other database work; that is acceptable for a single-user daily job. There is no streaming/download endpoint in M4, so `kanso backup --out DIR` is server-side only.
- The CLI's two new dependencies are `ureq` 3.5.1 (default features off, `rustls` + `rustls-webpki-roots`) for blocking HTTPS with bundled roots and no async runtime, and `toml` 1.1 for the config file; `serde` was already present. `ureq`'s HTTP-status-as-error behaviour is disabled so the CLI can read the API error envelope.
- The client config is `~/.config/kanso/config.toml` (0600), written atomically via a temporary file and rename. `KANSO_CONFIG` overrides the path; `KANSO_URL` and `KANSO_TOKEN` override the file independently (environment first, then file). `config init` calls `GET /api/me` before writing, prints the identity, and refuses an existing file without `--force` (exit 1). A remote URL must use `https://`; plain `http://` is accepted only for loopback hosts so the bearer token is never sent in cleartext to another machine.
- CLI exit codes: `0` success, `1` usage/start-up/config errors (including clap), `2` API errors (400, 401, 403, 404, 5xx plus network and local I/O), `3` every `409` and also `429 rate_limited`, which the brief groups with the conflict class. Runtime errors go to stderr as `kanso: <code>: <message>`; clap's own parse failures keep clap's format and exit 1. `--json` changes only stdout.
- `--json` is a global flag and prints the API response body byte-for-byte (plus a newline when missing) for 2xx responses; 204 prints nothing. Local-only commands (`config init`, `skill`) keep their plain output.
- `kanso propose` posts to `POST /api/tasks`: an agent token gets a proposal, while a human token creates an active backlog card because the API has no human-proposal path. The behaviour follows the token scope rather than pretending otherwise.
- `kanso depend REF on REF` reads the card, appends to its current `blocked_by` set and replaces the set, because the API's dependency endpoint is replace-only. `kanso check --done N` resolves the 1-based checklist position from the card then patches that item; `N = 0` is a usage error (exit 1), while an N beyond the checklist length is a `not_found` API-class error (exit 2).
- `kanso skill` with neither flag prints the skill. `--dir` without `--install` is a usage error. `--install` compares content: identical files are left untouched and reported `up to date`; different content is replaced atomically and reported `updated`, so the replacement is never silent and no `--force` is needed.
- The plan does not spell out `project add`/`edit` flags; M4 uses `--key`, `--name`, `--description`, `--repo-path` and `--color` so the CLI never has to guess positional order. `project show`, `task show` and `task list` output aligned plain-text tables or sections with no colour or ANSI.
- UTC timestamps needed by backup filenames and CLI tables are formatted by a small `src/time.rs` (civil-from-days), avoiding a date-time dependency.
- Review follow-ups: all CLI output goes through helpers that stop silently and exit `0` on `BrokenPipe` (other stdout write errors still exit `2`; stderr writes ignore a closed stream), an existing config with group/other permission bits is warned about and repaired to `0600` on load (a failed `chmod` exits `2`), `task show` prints the linked session id/directory/status, and `depend --help` says it needs a human token.

## M5 — OpenChamber adapter and integration settings

Verified against OpenChamber 2.6.0. Where §9 assumes a state this version does not expose, the intent is kept and the deviation is recorded here.

- The integration is enabled only when both `KANSO_OPENCHAMBER_URL` and `KANSO_OPENCHAMBER_TOKEN` are non-empty. Setting only one variable disables the adapter rather than failing startup, so the board remains usable without it. The token is never returned by the API and the `Config` debug output redacts it.
- The client lives in `src/adapter/openchamber.rs` (PLAN §13) and uses the existing blocking `ureq` dependency inside `spawn_blocking`; no new crate or build step. Dispatch waits 150 s (above the roughly two-minute worktree provisioning); the version probe waits 2 s, and session list/auto-accept 30 s. No HTTP call runs while the SQLite mutex is held.
- `GET /api/integration` is authenticated like the rest of the API. Disabled answers exactly `{openchamber:{enabled:false}}`; enabled adds `url`, `reachable` and `version`. `reachable`/`version` come from the public `GET /api/version`; a down or failing instance answers `reachable:false, version:null` and never fails the route. The probe is cached for 5 s behind a single-flight lock so the settings screen cannot hammer it.
- Deviation from §9's status table: OpenChamber 2.6's `session.status` returns only `busy` or `idle`, with no `retry`, `waiting-permission`, `waiting-question` or `failed`. The poller therefore makes one `session.list` call with `{withStatus:true,directory}` per distinct `session_directory` rather than one `session.status` call per card, and maps `busy` → `running`, `idle` → `idle`, idle with a non-success `outcome` → `failed` + attention. Waiting states are not detectable in 2.6; permission auto-accept is enabled on dispatch so they should not occur, and this limitation is accepted.
- Suspicious idle: idle, no non-success `outcome`, never observed busy and no assistant message. "Ever busy" is the poller's memory plus OpenChamber's `time.busy` field, which makes the check durable across restarts. Assistant messages are read from `metadata` only when the list response exposes them (`assistant_messages`, `assistant_message_count`, or `messages[].role == "assistant"`); 2.6 does not promise a transcript. A suspicious idle is marked `failed` with `attention=1` and an activity row rather than silently becoming review.
- A session that disappears from `session.list` counts as a per-session failure and becomes `offline` after three consecutive misses, so a vanished session cannot be polled forever. Three consecutive transport, HTTP or protocol failures for a directory mark every card in it `offline` + attention.
- Idle only auto-moves a card that is still `in_progress`, and the write re-reads the card inside the transaction, so a card the human moved to `in_review`, `blocker` or `done` keeps its column and only receives `session_status`/`attention`. `done` is never automatic.
- Automatic transitions write activity: `auto_moved` for the review move, `session_idle`, `session_failed`, `session_offline`, and `session_running` when busy is first recorded. `dispatched` and `permission_auto_accept_failed` cover the dispatch. Automatic and abandoned-session activity is attributed to `openchamber`, while `session_linked` and the dispatch keep the human principal. `session_running` is written only when a poll observes busy while the stored status was not already `running`; dispatch and the default manual link already store `running`.
- Auto-accept failure is recorded after the dispatch transaction and never undoes the stored session; the response includes the `permission_auto_accept_failed` activity when it can be written, otherwise the dispatch is still returned successfully.
- An in-memory per-card reservation stops two concurrent dispatch requests from creating two OpenChamber sessions/worktrees; the loser gets `409 already_dispatched`. The write-back transaction re-checks the claim, the card state, the column and the session id read before the upstream call, so a move, archive or manual session link the human makes while the call is running wins with `409 conflict` instead of being overwritten; an abandoned upstream session is logged and recorded as `dispatch_abandoned` activity. Entering `in_progress` clears `done_at`, `blocked_from` and `blocked_reason`.
- Dispatch is a human override and does not enforce the dependency gate that `claim` applies; the human chose the card explicitly. The card still has to be active and unclaimed.
- The poller runs every 10 s, only when the integration is enabled. It is one sequential loop (`Poller` owns its state and takes `&mut self`), so cycles cannot overlap, and it reads the work from SQLite on every tick so a restart resumes. The consecutive-failure and seen-busy counters are process-local and reset on restart; `time.busy` and the stored `session_status` carry the durable state.
- The worktree slug is lowercase ASCII `[a-z0-9-]`, collapsed and capped at 40 characters. A title with no ASCII letters or digits falls back to `task`, so the branch stays valid. Per §9 the payload always includes `branch: "kanso/REF-slug"`, including when `worktree` is `false`.
- OpenChamber 2.6 exposes no session URL to open, so the panel never invents one: it shows the session id, directory and status and offers a copy-id action. The pull-flow "link session" control is a small inline form using the existing human-only `POST /api/tasks/:ref/session`.
- The new settings route is `/settings/integration`; it is human-only like the other settings tabs. The card shows Dispatch only when the integration is enabled, the project has a non-empty `repo_path`, and the card is active and unclaimed. All new strings are in `web/i18n/en.js`.
- M5 integration tests run against an axum mock bound to `127.0.0.1:0`; they never contact the live `192.168.1.24:3000` instance.
